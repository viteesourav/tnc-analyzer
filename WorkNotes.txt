Goal of the Project:

Built an AI-powered Terms & Conditions analyzer using Spring Boot microservices with Kafka-based async processing, Redis caching, OAuth authentication, and rate-limited API Gateway. Extended with browser automation capabilities

Plan for the building the Project:

    1. Project Setup + Architecture
        -> Multi-module repo structure [3 different services under 1 service]
        -> Setup Docker + Docker Compose.
        -> Add Postgress Container
    
    All Services must be running in local

    2. Authentication (OAuth + Jwt)
        -> JWT Generation
        -> Google/Github OAuth
        -> Secure APIs

    Learn about the OAuth flow + Token based auth process
    
    3. Core APIs
        -> fake APIs for testing.
        -> Create actual APIs for POST /analyze + GET /result/{id} + GET /history.

    Learn API designs !

    4. DB Design + Cleanup
        -> Design Schemas to store the responses.
        -> tables: users & analysis.

    5. Async + Infra Enhancements
        -> Add Kafka (docker) + Producers in analsis-service + Consumer (new Service: worker) 

    Learn Event Driven Architecture & Message Flow

    6. AI Integration
        -> Integrate google GemniAI or OpenAI [Anything that is free to use]
        -> Prompt Designing

### Steps to Start & Run the Application:

    1. First if it's a fresh run: 
        -- Install wsl [wsl --install in cmd] & install Reancher Desktop.
        -- Then in the project dir: We have docker-compose.yml
        -- open cmd: 
            docker compose up -d 
        -- The above spins up the Postgress 16 and other Infra.
    
    2. Go to application.yml of analysis-service: 
        - update the GEMINI_API key to your Gemini_API_KEY.
        - Location: https://aistudio.google.com/api-keys
    
    3. Open 3 seperate cmd: 
        - ./gradlew :analysis-service:bootRun
        - ./gradlew :auth-service:bootRun
        - ./gradlew :api-gateway:bootRun

    4. Once the services are up & running: 
        - Open the Postman Collection in Postman.
        - Steps:
            1. APIs are protected: Hit the login API first.  --> You get JWT token.
                - If new user -> Register the user First.
            2. then With the token:
                -> hit /analysis with the JSON payload.  

    5. To stop all running services:
        - open cmd:
            ./gradlew --stop 
        - Send command to all gradlew services to stop !!

                WebClient is a modern, non-blocking, reactive HTTP client included inside the WebFlux dependency. It is used to make HTTP calls to external APIs or other microservices. [** IMP **]
            -> Difference between WEb-Client Vs REST Template:
                1. non-blocking
                    -- If your service calls an external API that takes 5 seconds to respond, RestTemplate will freeze that execution thread for the entire 5 seconds. 
                    -- WebClient fires the request, immediately frees up the thread to handle other tasks, and executes a callback whenever the external API finally responds.
                2. Support both async and sync workflows
                    -- Even if you aren't building a fully reactive application, you can still use WebClient in a standard blocking application by appending .block() at the end of the call chain.
                3. Standard Practise.
                    -- Spring has officially deprecated RestTemplate into maintenance mode, making WebClient the designated tool for HTTP communication in modern Spring apps.

    -- Pagiantion, Sorting, Fitlering, searching with Keyword APIs on Analyses:
        NOTE:
            -- Important Architectural Pattern here: So to implement the above data handling methods we got 2 options:
                1. Let the same url handles it.
                    eg: GET /analyses?
                             page=0&&size=10
                             &riskLevel=?
                             &keyword = ?

                2. for each of them different urls exist.
                    GET /analyses/high-risk
                    GET /analyses/search
                    GET /analyses/filter
            -- Advantages of using Option 1 over Option 2:
                - As the system scales, APIs will be easier to maintain.
                - easy to extend, Industry stnadards.
                - Frontend can combine filters naturally.
            NOTE:
                - When we combine multiple filter items as RequestParams to the same url. One thing we should remember:
                    
                    "all this filter options are optional, always define default values for them"


        1. Pagiantion:
            -- with time data might grow -> It's better to receive the data in chunks. first 50, then 100, and so on.
            -- enpoint URL:
                GET analyses?page=0&&size=10  --> Fetches first 10 records in the list.
                GET analyses?page=1&&size=10  --> Fetches next 10 records in the list.
            -- Appraoch:
                1. First change the JPARepo method from custom method call to use Pageable to received sorted dynamically data using Page & pageable.
                    - spring receives sorted records dynamically from pageable.
                    - spring data JPA, understands you added pageable here -> it automatically adds LIMT and OFFSET Clause in the SQL.
                    eg: 
                        SELECT * FROM analysis_result WHERE username = ?
                        ORDER BY created_at DESC LIMIT 10 OFFSET 0;
                2. Serice Layer: it will not be "List", it is "page" now --> page.map also exist.
                3. Controller: we will be adding new RequestParams -> page and size and provide their default values.
            -- New things used:
                - Page, pageable, PageRequest.of(), Page.map() from org.springframework.data.domain.
        
        2. Filtering + Searching Support:
            NOTE:
                -- Now Traditional Approach is for each of this usecase, you add additional methods in the JPARepository. -> Which is correct and it will work.
                -- But new functionality -> again new methods in JPA -> overhead to maintain all this over time.
                Solution:
                    JPA Specifications:
                        -> This is very common "enterprise pattern". You build it like a lego block -> add whatever needed only.
                        -> username filter + Risk filter + keyword filer + Date Filter (Future scope) + Safety score Filter (Future Scope).
                Advantages:
                    -- Specifications allow us to build dynamic queries by combining reusable predicates at runtime, avoiding repository method explosion and making filters highly extensible.
                Appraoch:
                    1. First you add JPASpecificationExecutor to the JPARepository: This gives ability to pass Specification object to all standard findAll() queires.
                        -- JpaRepository handles:
                            save()
                            findBy()
                            delete()
                            findAll()
                        -- JpaSepecificationExecutor adds:
                            findAll(specification spec)
                            findAll(specification spec, Pageable pageable)
                            count(spec)
                            exists(spec)
                    2.  Create a new specification package:
                        -> this one class AnalysisResultSpecification will hold multiple filter builder.
                        -> Inside the class -> define your own spefication method:
                            -- with the params it would expects like username, riskLevel or keyword filter values.
                            -- then inside it you can have the logic to chain this multi-filter implementations.
                            eg:
                                root                        ---> from analysis_result.
                                root.get("username")        ---> analysis_result.username 
                                criteriaBuilder.equal(...)  ---> where usename = ?
                            so this below means:
                                criteriaBuilder.equal(root.get("username"), username)  --> where usename = 'john';
                    3. In Service Layer:
                        -> build the specification -> check the input received and build the filter chain.
                        -> then instead of calling the individual derived method, use findAll(specification, pageable).
            
        3. Dynamic Sorting:
            -- Accept Additional inputs from Client, on the sortBy and Sort direction -> ascending or descring.
            -- In Service Layer: Instead of hardcoding the PageRequest, dynamically create the Sorting.

        -- Difference between JPQL vs SQL:
            SQL queires database tables directly, whereas JPQL queries JPA Entities and their mapped fileds, making it database-independently.
            eg:
                JPQL queries will only work on fields defined in AnalysisResult DTO. NOTE: in enity file, we can define custome names to database columsn. eg: @Column(name = ?)
            -- While writing JPQL, we have to consider the Entity fields only not the columnd name in SQL table.
            -- JPQL itself doesn't talk to your database. When you run a JPQL query, Hibernate intercepts it and translates it into the native SQL dialect of whatever database is currently connected.
               This translation is handled by a configuration property called the Database Dialect.
            Advantage:
                -> This works very well when you switch database. -> If we write native SQL then it might break but with JPQL using JPA entity fields -> no matter what database you connect it will take care i.e Database-independent.
                -> This gives us Advantage to switch the entire underlying database, without changing a single line of Java code. [ Crazzy !!! ]
